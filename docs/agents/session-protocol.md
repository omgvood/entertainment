# Протокол сессии

Правила о том, как ведётся работа. Что делать в конкретной задаче — в тикете; какой скилл брать — в `skills-routing.md`.

Разбор инцидентов, из которых эти правила выросли, — `docs/agents/process-journal.md`.
Журнал в сессию не подаётся: всё действующее лежит здесь или в `CLAUDE.md`, журнал
отвечает только на вопрос «почему правило такое».

## R-01. Сверка состояния — до всего остального

Перед исследованием, планированием и первой правкой:

```
git log --oneline origin/master..master
git status -sb
git worktree list
```

Карта, тикет или отчёт, построенные от `origin/master`, врут, если локальный `master` ушёл вперёд.

**Сломалось, если:** цифры в задаче не сходятся с репозиторием или БД; тикет описывает работу, которая уже в `master`.

## R-04. Ветка и worktree живут ровно до мерджа

Уборка — **шаг закрытия сессии, а не команда git.** Мердж часто происходит кнопкой на GitHub, вне сессии-владельца worktree, поэтому «после мерджа приберись» само не срабатывает.

Порядок после слияния PR:

1. Закрыть сессию/вкладку, которая держит worktree — иначе `git worktree remove` падает с `Device or resource busy`.
2. `git worktree remove <путь>`
3. `git branch -d <ветка>`
4. `git pull --ff-only` в основном чекауте — мердж-коммит с GitHub сам туда не приходит.

Worktree, в котором не оказалось работы, убирается так же — мерджа ждать не нужно.

Уборка нужна не только после мерджа. Claude Code заводит ветку `claude/<имя>-<hex>` от `origin/master` и worktree под неё **в момент старта сессии**, независимо от того, сделает сессия работу или нет. Сессия, которая ничего не закоммитила, оставляет такой worktree навсегда: мерджа не будет, значит и триггер «после мерджа» не наступит. За 2026-09-20 так накопилось три штуки.

Проверка автоматическая: `scripts/process-check.ps1 -Mode stop` висит на Stop-хуке и при закрытии сессии называет worktree без коммитов и ветки, пережившие мердж. Worktree с незакоммиченными изменениями считается живым и не называется. Одна и та же находка называется сессии один раз — повторяющееся слово в слово замечание перестают читать. Хук не убирает ничего сам: он не даёт пропустить уборку молча.

**Сломалось, если:** `git worktree list` показывает запись без открытого тикета в волне; `git worktree remove` падает с `Device or resource busy`.

## R-05. Три открытых задачи, детализация на одну волну вперёд

Одновременно открыто не больше трёх тикетов: одна блокирующая плюс две дешёвые параллельные. Остальное живёт одной строкой в тумане карты и расписывается, когда до него дойдёт очередь.

Между отчётом с находками и тикетами обязателен шаг **сведения**: один экран, три-семь проблем, у каждой строка «что не так» и метка (блокирует остальное / дёшево и независимо / дорого и спорно). Человек выбирает волну. Без этого шага тикеты писать нельзя.

**Сломалось, если:** тикетов со `Status: open` без `## Answer` в активном эффорте больше трёх (`Status: backlog` не считается — иначе признак срабатывает на всём бэклоге и перестаёт что-либо различать); «не понимаю, с чего начать»; задача переписана второй раз до того, как до неё дошли руки.

## R-06. Названные пути существуют

Любой путь, упомянутый в `CLAUDE.md`, `skills-routing.md` или этом файле, обязан существовать на диске и быть трекаемым. `CLAUDE.md` месяцами ссылался на `.scratch/`, которого никогда не было, — расхождение было молчаливым.

`docs/` — ровно четыре папки: `agents/`, `superpowers/`, `research/`, `personal/` (не трекается). Файл, попавший в `docs/` мимо них, git не увидит — это сигнал, что он не на своём месте.

**Сломалось, если:** путь из этих файлов не открывается; в `docs/` появился файл вне четырёх папок.

## Последовательность, которая работает

0. **Сверка состояния. До всего остального.** Где код (`git log --oneline origin/master..master`), что влито, что на проде, что в БД. Десять минут, которые снимают половину будущих ошибок. `R-01`
1. **Вопрос и границы.** Что решаем, что сознательно не решаем. Одним абзацем, до исследования.
2. **Исследование.** Факты и цифры. Результат — отчёт, а не план.
3. **Сведение. Главный пропущенный шаг.** Один экран: три-семь проблем, у каждой одна строка «что не так» и метка — блокирует остальное / дёшево и независимо / дорого и спорно. Выбирается первая волна: одна-три задачи. Человек подтверждает.
4. **Декомпозиция только выбранной волны.** Тикеты пишутся на одну волну вперёд. Остальное живёт одной строкой в тумане. `R-05`
5. **Исполнение.** Один тикет — одна сессия — одна ветка (worktree от `master`). Локализация грепом до первой правки. `R-02`
6. **Ревью перед мерджем.** Даже для тикета в одну строку — проверить дифф до слияния в `master`, не после. Здесь же `## Answer` в тикете и строка в карте.
7. **Мердж и закрытие.** Сразу после слияния: закрыть сессию, державшую worktree, затем `git worktree remove <путь>` + `git branch -d <ветка>`. `R-04`
8. **Возврат к шагу 3.** Новое сведение с учётом того, что узнали, плюс аудит реестра правил.

Главный принцип: **детализировать ровно на одну волну вперёд**. Карта с туманом — нормальное состояние, а не недоделка.

## Сигналы

Читаются по ходу работы и прогоняются чеклистом в конце волны. Таблица ведёт от симптома к
правилу и не содержит критериев: что именно считается нарушением, написано в блоке
«Сломалось, если» у самого правила.

| Сигнал | Куда идти |
|---|---|
| «Не понимаю, с чего начать» | пропущен шаг сведения — «Последовательность», шаг 3 |
| Открытых задач больше, чем помещается на экран | R-05 |
| Задача переписывается второй раз, пока до неё не дошли руки | R-05 |
| Цифры в задаче не сходятся с репозиторием или БД | R-01 |
| В одном чате обсуждаются фронт, парсер и процесс | смешаны слои, чат надо делить |
| Веток или worktree больше, чем активных тикетов | R-04 |
| `git worktree remove` падает с «Device or resource busy» | R-04 |
| Уборка ветки после мерджа началась со слов человека, а не хука | R-04 |
| Тест упал после правки, и его файл не был назван в тикете | R-02 (`CLAUDE.md`) |
| После закрытия тикета греп по значению находит места со старым смыслом | R-02 (`CLAUDE.md`) |
| Запрос из тикета не выполнился с первого раза | R-03 (`_ticket-template.md`) |
| В «Готово когда» стоит «A или B» — исполнитель выбирает сам | `process-journal.md`, INC-08 |
| Запущен `/to-spec`, `/to-tickets`, `/implement`, `/triage` или `grill-with-docs` | `process-journal.md`, INC-03 |
| Путь из `CLAUDE.md` или `skills-routing.md` не открывается | R-06 |
| В `docs/` появился файл не в одной из четырёх папок | R-06 |

**Как чинить на лету:** остановиться, не добавлять новых задач, свести открытое к трём
пунктам, выбрать один, остальное убрать в туман.

## Шаблон открытия чата по тикету

```
Возьми тикет docs/superpowers/wayfinder/<эффорт>/issues/<файл>.md
Карта: docs/superpowers/wayfinder/<эффорт>/map.md
Порядок работы: docs/agents/session-protocol.md, локализация — по CLAUDE.md.

Скилл в шапке тикета: <имя>.
До первой правки сделай собственный греп по символу и по значению,
результат запиши строкой «Локализация: <команда>, найдено N мест» в ## Answer.

В конце: ## Answer в тикет и строка в Decisions so far карты.
Без моего согласия не пушить.

Отметь, какую ветку ты получил.
```

Обновлено после волны 1 — это промпт, которым реально открывалась сессия тикета 02. Прежняя версия не называла ни скилл, ни локализацию, а R-02 проверяется самоотчётом: если промпт о нём не напоминает, правило держится только на том, вспомнит ли сессия строку из `CLAUDE.md`. Строка «отметь, какую ветку ты получил» — дешёвый способ увидеть в первом же ответе, завёл ли харнесс свою `claude/*` ветку (Q6).

## Аудит в конце волны

После закрытия волны, до нового сведения: пройти по «Сломалось, если» всех правил здесь и в `CLAUDE.md`, обновить счётчик повторов в реестре журнала.

Решение по счётчику, а не по ощущению: 0 повторов за три волны — правило закрывается; 1 — уточняется формулировка; 2 — правило **поднимается уровнем** (этот файл → `CLAUDE.md` → хук), текст не переписывается.
