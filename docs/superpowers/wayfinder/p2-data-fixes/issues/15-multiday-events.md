# Многодневные события: дата начала и конца

Type: grilling
Скилл: superpowers:brainstorming — решение меняет модель данных
Status: resolved
Blocked by: —

## Question

Фестивали лежат одной строкой на дату начала, поэтому со второго дня исчезают из ленты. Решить, как представлять событие, которое идёт несколько дней.

## Контекст

- Примеры в данных: «Пермская Фантасмагория» 1–7 октября (строка на 1 октября), «МОНОфест» 9–12, «Музейные дни» 12–16, фестиваль Спивакова 23–27, цирк «Империя мастеров» 5–20 сентября.
- В схеме есть только `date` (text) — поля конца нет. Выставки при этом приходят строкой на каждую дату, то есть один и тот же смысл выражается двумя разными способами.
- Варианты: колонка `date_end`; разворачивание в строки по дням на стороне парсера; вычисление диапазона на фронте из описания (ненадёжно).
- Влияет на ленту дат P1 (в какой день показывать), на «ещё N дат» и на «идёт сейчас» (тикет 06).
- Цена ошибки в обе стороны: развернуть в дни — «Музейные дни» займут пять дней ленты; оставить одной строкой — фестиваль не найти на третий день.

## Готово когда

Записан ответ: форма хранения, кто её заполняет, что делает фронт и нужен ли бэкфилл. Миграция и код — отдельными тикетами.

## Answer

Локализация: `grep -n "date_start|date_end|\bdate\b" parser/src/parser/models.py` — 4 места (`models.py:33,69,77,130`, схема и валидатор); `grep -rl "\.date\b|series|otherDates"` во фронте (`web/lib/eventTiming.ts`, `EventCard.tsx`, `CityView.tsx`, `web/lib/series.ts`, `series.test.ts`, `app/{sochi,perm}/events/[slug]/page.tsx`, `search.ts`) — 8 файлов. Ключевая находка: выставки уже несут многодневность строкой-на-каждый-день, а `web/lib/series.ts::otherDates` уже группирует события с одинаковыми title+venueName по разным `date` и считает «ещё N дат» — механизм для многодневных событий во фронте уже есть и работает, просто фестивали в него не попадают, потому что парсер кладёт только одну строку на дату начала.

Решение: **не заводить `date_end`.** Разворачивать многодневные события в парсере в одну `EventRow` на каждый день диапазона — тот же паттерн, что уже применяется к выставкам, без новых полей в схеме и без нового кода на фронте (`series`/`otherDates` подхватят их автоматически).

1. **Форма хранения.** Никакой новой колонки. Диапазон существует только на входе в парсер (`date_start`/`date_end`, оба `YYYY-MM-DD`), на выходе — N строк `EventRow` с разными `date` и одинаковыми title+venue+slug-основой (как уже происходит для выставок).
2. **Кто заполняет.** LLM-промпт получает второе поле диапазона (`date_end`, по умолчанию равно `date_start` для однодневных — обратная совместимость без миграции промпта под старые источники). Парсер (в `to_event_row` или на шаг раньше) разворачивает `[date_start, date_end]` в список дат и создаёт по строке на каждую.
3. **Граница на длину диапазона.** Ограничить разворачивание 21 днём (три недели): «Музейные дни» (5), «Пермская Фантасмагория» (7), «МОНОфест» (4), фестиваль Спивакова (5), цирк «Империя мастеров» (16) — все укладываются. Диапазон длиннее 21 дня — сигнал, что LLM спутала фестиваль с сезоном/абонементом, а не факт многодневного события: такие остаются одной строкой на `date_start`, дата конца отбрасывается, в лог — warning для последующей проверки вручную.
4. **Бэкфилл.** Не нужен. Уже записанные в БД фестивали (одна строка на дату начала) сами получат недостающие дни на следующем ежедневном прогоне: `source_url` жив, событие ещё не прошло, upsert по новому slug каждого дня добавит остальные строки, не трогая существующую.
5. **Что делает фронт.** Ничего нового — `series.ts::otherDates` уже умеет схлопывать одинаковые title+venue в «ещё N дат»; лента дат и P1-код получают многодневные события бесплатно, как получают выставки сейчас.

Влияние на связанные тикеты: тикет 06 («идёт сейчас») получает для многодневных событий тот же набор строк по датам, что и для остальных — политика применяется без изменений, отдельного случая для диапазонов не нужно.

Код — отдельным тикетом: второе поле в промпте (3 экстрактора), разворачивание в парсере (вероятно рядом с `to_event_row` или отдельная функция `expand_date_range`), тест на 21-дневную границу.
