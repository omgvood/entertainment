# Цена в схеме: бесплатно против неизвестно

Type: grilling
Скилл: superpowers:brainstorming — решение меняет схему БД и промпты парсера
Status: resolved
Blocked by: 01, 10

## Question

Решить, как «цена неизвестна» записывается в данных, а не выводится каждым потребителем заново из строки: колонка `price_unknown`, `NULL` вместо нуля или что-то третье. Плюс что при этом должен писать LLM.

## Контекст

- `price_min` / `price_max` в `ParsedEvent` — обязательные `int >= 0` (`parser/src/parser/models.py:36-37`), поэтому «неизвестно» записать нечем, и модель ставит 0.
- Промпты не говорят, что делать при неизвестной цене (`deepseek_extractor.py:56`, `groq_extractor.py:68`, `gemini_extractor.py:42`), отсюда `price_text` вида «0 ₽».
- README, пункт 18, предлагает заполнять новую колонку «тем же правилом», что в `price.ts`. Правило до тикета 01 включает `0 ₽` — в этом виде ошибка переедет в БД.
- Пункт блокирует фазу 2 поиска (README, пункт 12): разбор «до 1000 рублей» на данных, где 39% без цены.
- `jsonld.py:236` и `timepad.py:228` пишут «бесплатно» при `pmin == 0` — проверить, не тот же ли это ложный ноль.

## Готово когда

Записан ответ: форма хранения, правило заполнения парсером, формулировка в промптах, нужен ли бэкфилл накопленных строк и что делает фронт после появления колонки. Миграция и код — отдельными тикетами.

## Answer

Решено 2026-09-22 через `superpowers:brainstorming` (архитектурная глубина, без отдельного spec-файла — решение фиксируется в тикете по конвенции карты).

Локализация: `grep -rn "price_min|price_max|ParsedEvent"` (символ, 50 файлов), `grep -rn "₽|бесплатн|цена (не )?известна|price_text"` (значение, 60 файлов); по существу решения — `parser/src/parser/models.py:36-38` (`price_min`/`price_max` — `int, ge=0`, не nullable), три промпта LLM (`deepseek_extractor.py:56,88`, `groq_extractor.py:67,99`, `gemini_extractor.py:41,68` — сейчас ни слова про «цены нет»), структурные экстракторы `jsonld.py:221-239` и `timepad.py:214-231` (не LLM, цена `0` в `offers`/`ticket_types` → `"бесплатно"`, пустой список → `"уточняйте"`), фронт `web/lib/price.ts` (текущая regex-эвристика над `price_text`, потребители — `web/lib/filters.ts:87`, `web/lib/search.ts:67`).

**Ключевой факт, определивший решение.** Тикет 10 (resolved) показал: регексп по `price_text` как признак «бесплатно» ненадёжен — из 28 проверенных по первоисточнику событий подтвердилось 25%, в 46% источник продавал билеты, а слова «бесплатно» в посте не было вообще — это немотивированная галлюцинация LLM при заполнении `price_text`, а не спутанные соседние слова. README (пункт 18) предлагал заполнять новую колонку «тем же правилом» — это узаконило бы ту же галлюцинацию в схеме, поэтому отклонено.

**1. Форма хранения.** Enum-колонка `price_kind` (`known` / `free` / `unknown`), `NOT NULL DEFAULT 'unknown'`. Не булев `price_unknown` — `free` и `unknown` разные состояния для UI и поиска (три ветки, не две), булева пары недостаточно.

**2. Правило заполнения парсером.** LLM-экстракторы получают новое обязательное поле наравне с `price_min/price_max/price_text`:
- `known` — в тексте есть конкретная сумма → `price_min/max` = она.
- `free` — источник дословно говорит «бесплатно» / «вход свободный» / «участие бесплатное» → `price_min=price_max=0`.
- `unknown` — цена не упомянута, «по запросу», «уточняйте», либо продажа билетов есть, а суммы нет → `price_min=price_max=0`.

Структурные экстракторы (`jsonld.py`, `timepad.py`, не LLM) логику не меняют: цена `0` в `offers`/`ticket_types` → `free`; пустой список цен → `unknown` (сейчас `"уточняйте"`).

**3. Промпты.** В `deepseek_extractor.py`, `groq_extractor.py`, `gemini_extractor.py` добавляется инструкция с этим правилом и примерами; ключевая фраза — «`free` только если в тексте буквально есть слово о бесплатности, не по умолчанию» — прямое следствие вывода тикета 10.

**4. Бэкфилл.** Все существующие строки → `price_kind = 'unknown'` при миграции (вариант A). Backfill старым регекспом (вариант B) отклонён — перенёс бы доказанную тикетом 10 галлюцинацию (46% ложных «бесплатно») прямо в новую колонку, обесценив п.1–3. Минус варианта A: часть из 208 строк со словесным признаком в `price_text` временно перестанут находиться по фильтру «бесплатно», пока событие не переизвлекут — приемлемо, т.к. события живут в базе ограниченный срок (будущие события Перми/Сочи).

**5. Фронт.** `web/lib/price.ts::priceKind()` перестаёт быть regex-эвристикой над `price_text` — читает колонку `price_kind` напрямую (typed passthrough), `FREE_RE` удаляется. `web/lib/filters.ts:87` и `web/lib/search.ts:67` не меняются: они уже потребляют результат `priceKind()`, а не саму строку.

**Вне scope этого тикета (код-тикет отдельно):** точный SQL-тип в Postgres (`text` + `CHECK` или нативный `ENUM`), имя и порядок миграции, нужно ли принудительно ре-парсить существующие ~39% «без цены» строк для ускорения перехода с `unknown`, надёжность признака `free` у структурных источников (`jsonld`/`timepad`) — цена `0` в `offers` не проверена тикетом 10 и может быть таким же ложным нулём площадки, отдельная проверка не делалась.
